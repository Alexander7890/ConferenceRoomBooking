# Коротка документація проєкту ConferenceRoomBooking

## 1. Бізнес-завдання

Система допомагає керувати конференц-залами, їхньою місткістю, погодинною ціною та доступними додатковими послугами. Вона знаходить вільні зали, створює бронювання без конфліктів, автоматично розраховує вартість і надає бізнес-аналітику.

## 2. Основні можливості

- Створення, перегляд і редагування залів, зокрема списку доступних послуг. Видалення деактивує зал і зберігає його історичні бронювання.
- Перегляд активних послуг через `GET /api/services`. Окремого CRUD послуг немає.
- Пошук активних залів за часом і мінімальною місткістю через `GET /api/rooms/available`.
- Створення бронювання через `POST /api/bookings` із перевіркою вибраних послуг, доступності залу та розрахунком повної вартості. Окремого endpoint для попереднього розрахунку ціни немає.
- Звіти про дохід, використання залів і популярність послуг.
- Демонстраційна HTML/CSS/JavaScript сторінка з розділами Rooms, Availability, Booking та Reports. Форми працюють із реальним API через Fetch API; вартість повертає backend.

Бронювання та пошук доступності використовують місцевий час залу без `Z` або часового зсуву, наприклад `2026-10-01T11:00:00`. Початок і завершення мають бути в один календарний день, у межах 06:00–23:00; завершення — пізніше початку.

На порожній БД створюються Зал А (50 осіб, 2000 грн/год), Зал B (100 осіб, 3500 грн/год) та Зал C (30 осіб, 1500 грн/год). Кожному доступні Проєктор (500 грн), Wi-Fi (300 грн) і Звук (700 грн). Seed додає відсутні записи за назвою, не перезаписує наявні дані та не відновлює змінений користувачем набір послуг існуючого залу.

## 3. Розрахунок вартості

Розрахунок використовує базову погодинну ціну залу та такі коефіцієнти:

| Час | Тариф |
|---|---|
| 06:00–09:00 | Знижка 10%: базова ціна × 0,90 |
| 09:00–12:00 | Базова ціна |
| 12:00–14:00 | Пікова націнка 15%: базова ціна × 1,15 |
| 14:00–18:00 | Базова ціна |
| 18:00–23:00 | Знижка 20%: базова ціна × 0,80 |

Бронювання ділиться на частини за межами тарифних періодів; кожна частина оплачується за фактичною тривалістю. Піковий тариф замінює стандартний у проміжку 12:00–14:00. Підтримуються неповні години: 30 хвилин за стандартним тарифом коштують половину погодинної ціни.

Наприклад, для ставки 2000 грн/год бронювання 11:00–15:00 коштує `2000 + 2000 × 1,15 × 2 + 2000 = 8600 грн` без послуг. Ціна кожної вибраної послуги додається один раз за бронювання.

`PricingCalculator` рахує в `decimal`; сумарна оренда округлюється до копійок після складання тарифних частин. `Booking.TotalPrice` та `BookingService.PriceAtBooking` зберігають історичні суми, тому майбутня зміна тарифів не змінює вартість уже створеного бронювання.

## 4. Звіти та аналітика

Усі звіти приймають `from` і `to`, де `to > from`, та враховують бронювання з початком у проміжку `from <= StartDateTime < to`. Наприклад, для жовтня передайте `from=2026-10-01T00:00:00` і `to=2026-11-01T00:00:00`. Агрегації виконуються в БД і включають історію неактивних залів та послуг.

| Endpoint | Що показує | Користь для бізнесу |
|---|---|---|
| `GET /api/reports/revenue` | Загальна вартість бронювань, їхня кількість і середній чек | Оцінка обсягу бронювань та середньої вартості замовлення |
| `GET /api/reports/rooms` | Кількість бронювань, заброньовані години та дохід для кожного залу | Порівняння завантаженості залів і визначення найпопулярніших просторів |
| `GET /api/reports/services` | Кількість виборів кожної послуги та її історична вартість у бронюваннях | Виявлення затребуваних послуг і оцінка їхнього внеску в дохід |

Дохід у загальному звіті та звіті залів включає додаткові послуги. Звіт послуг показує цю складову окремо, тому його суми не потрібно додавати до загального доходу. Це вартість створених бронювань; обліку фактичних платежів у проєкті немає. Кількість активних залів і їхня сумарна місткість також відображаються у вебінтерфейсі.

## 5. Технічні рішення

- **Backend:** C#, .NET 10, ASP.NET Core Web API з Controllers. Domain містить сутності; Application — DTO, перевірки та бізнес-логіку; Infrastructure — EF Core, repositories і ініціалізацію БД; Api — HTTP, обробку помилок і статичний інтерфейс. Тести розміщені в окремому проєкті та використовують xUnit.
- **База даних:** MySQL 8.4, Entity Framework Core 10 і `MySql.EntityFrameworkCore`. Зв’язки залів та послуг, бронювань та послуг зберігаються в окремих таблицях.
- **Запуск:** Docker Compose запускає API та MySQL; healthcheck затримує запуск API до готовності БД. Дані зберігаються в `mysql_data`. Налаштування передаються через локальний `.env`, який не входить до Git.
- **Ініціалізація:** за `APPLY_MIGRATIONS=true` застосовуються EF Core migrations, після них виконується seed. Окреме налаштування `Database:SeedOnStartup` дозволяє запускати лише seed; без явного ввімкнення ці дії не виконуються.
- **API-документація:** вбудований генератор ASP.NET Core створює `/openapi/v1.json`, а Swagger UI показує цей самий документ за `/swagger`. Обидва маршрути доступні в Development, зокрема в поточному Compose deployment.
- **Validation:** Application перевіряє вхідні значення, часові межі, унікальність і доступність послуг. Контролери повертають DTO; помилки оформлюються через ProblemDetails із кодами 400, 404, 409 або 500, без внутрішнього stack trace.
- **Конфлікти:** інтервали перетинаються, якщо початок нового бронювання раніший за кінець існуючого, а його кінець пізніший за початок існуючого. Сусідні інтервали, наприклад 10:00–12:00 і 12:00–13:00, дозволені. Створення бронювання виконується в транзакції `ReadCommitted` з блокуванням рядка залу через параметризований `SELECT ... FOR UPDATE`, що послідовно обробляє конкурентні запити на той самий зал.
- **Ціна:** окремий `PricingCalculator` виконує сегментний розрахунок; JavaScript не дублює формули. Авторизація, оплати та скасування бронювань на цьому етапі не реалізовані.

## 6. Запуск

Встановлення Git і Docker Desktop, клонування, налаштування `.env`, запуск та безпечна зупинка описані в [README.md](README.md).
